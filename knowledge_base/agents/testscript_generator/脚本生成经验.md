# 脚本生成经验

本文档用于沉淀本次 Midscene + Playwright 自动化脚本编写、调试、修复过程中已经验证成功、可稳定复用的经验，既覆盖价格计算字段验证，也补充审批流端到端脚本的稳定实现方法，目标是为后续扩展更多业务链路提供一套可复用的方法。

## 0. 生成脚本前的速查清单

- 先分层：页面交互、字段提取、业务校验、视觉断言不能混写。
- 先判控制权：关键状态控制、公式计算、精确断言优先交给 Playwright。
- 再判 AI 价值：aiQuery 只做局部去索引化，aiAssert 只补渲染层，aiAction 不接管关键恢复主链路。
- 先稳住编辑态：同一条业务链尽量共用同一个编辑页，优先在当前页恢复，不要反复切用户、重开新页。
- 先局部后 AI：凡是用 aiQuery，都必须先通过 page.evaluate 缩小到目标区域，再关闭 screenshotIncluded 和 domIncluded。
- 先公式后结论：所有价格、折扣、数量字段最终都要回到业务公式校验，不能只信提取结果。
- 先分流问题性质：脚本阻碍、业务差异、精度差异不是一类问题，处理方式必须分开。
- 先定提交成功信号：提交动作必须以“无拦截 + 限定时间内出现成功 toast”作为唯一成功标准，不能用 URL 变化或弱跳转代替。
- 先分清业务拦截类型：UNC、AI 提示、服务商专供产品、表单缺失项不是一类问题，必须分别识别、分别处理。
- 先锁定弹窗作用域：处理关闭、知道了、确定这类按钮时，只能在当前可见弹窗内部点击，不能整页泛搜后直接点。
- 先重取再等待：页面填值后如果会重渲染，后续轮询必须重新抓当前 locator，不能一直盯着旧句柄。
- 先收口再继续：恢复逻辑最终必须收口到可验证业务态，例如确认目标编辑页关键区域已经可见。

## 1. 本次场景的核心结论

- 脚本里不要把“页面交互”“字段提取”“价格校验”混成一团，必须拆开处理。
- 页面上结构稳定、定位清晰、值本来就存在于 input 或表格里的字段，优先使用 XPath 或 DOM 直接读取，不要先走 AI。
- 页面上汇总区、描述区、展示形式容易混淆的字段，可以保留 AI，但一定要先缩小范围，只给 AI 看目标区域的文本。
- 所有价格字段提取后都要做业务校验，不能只信提取结果本身。

## 2. 已验证有效的成功经验

### 2.1 复用已登录浏览器比重登更稳

- 使用 chromium.connectOverCDP 连接已经打开的调试浏览器，可以直接复用 Cookie 和登录态。
- 这样做可以把问题聚焦在页面交互和字段提取本身，避免登录流程影响调试效率。

### 2.2 先选对业务页面，再执行自动化

- 一个浏览器上下文里可能有多个页面，不能默认取第一个 page。
- 通过 pickWorkingPage 排除 chrome-extension:// 和 about:blank 后，再挑真实业务页，稳定性明显更高。

### 2.3 “没有渠道参与”这类点击要做多策略兜底

- 单一绝对 XPath 点击容易超时。
- 更稳的顺序是：先按文本或 label 点击，再退回 XPath，最后用原生事件兜底。
- 这类元素经常出现在复杂表单、iframe、嵌套组件中，必须允许多种定位方式共存。

### 2.4 弹窗列表里的数量输入要按产品行精确定位

- 弹窗里同类 input 往往不止一个，不能直接用一个宽泛 XPath 去填数量。
- 正确做法是：先按型号找到目标行，再在该行内部找数量输入框。
- 这能避免 strict mode violation，也能避免把数量填到错误的产品行。

### 2.5 产品明细字段优先直接读主表 input

- 当前页面里的“用户价格”和“数量”在主表中都有明确 input，可直接读取。
- 这类字段采用 readNumericInputValue 之类的统一读取函数最稳。
- 统一做去逗号、转数字、校验合法性，能减少后续比较时的类型问题。

### 2.6 汇总字段保留 AI，但必须先限定到目标区域

- 当前“总用户价格”如果让 AI 看整页，误判概率很高。
- 已验证有效的方式是：先通过 page.evaluate 只取 id="PrceInfo" 节点里的文本，再把这段文本交给 aiQuery。
- 同时关闭 screenshotIncluded 和 domIncluded，让 AI 不再参考整页截图和整页 DOM。
- 这相当于把 AI 从“整页猜测”改成“局部文本抽取”，准确率明显提高。

### 2.7 价格校验必须回到业务公式

- 提取出单价、数量、总价后，必须做 expectedTotal = userPrice × quantity 的显式校验。
- 只要最终业务关系不成立，就应该判失败，而不是认为 AI 提取到数字就算成功。
- 这是后续扩展更多字段时最重要的兜底手段。

### 2.8 日志和报告要保留，方便反查

- Midscene 运行报告、AI 调用日志、模型配置日志都非常有用。
- 当提取值不准时，先看 AI 实际拿到了什么文本，再看它是如何推理出错误结果的。
- 以后验证更多字段时，也建议继续保留中间结果日志。

### 2.9 产品表“去索引化”是有价值的，但必须是“局部快照 + 语义提取”，不是把整页扔给 AI

- 当产品表列顺序可能调整、增减列、标题文案有轻微变化时，继续写死 cells[2]、cells[5] 这类索引会越来越脆。
- 本次验证下来，比较稳的做法不是“整页 aiQuery”，而是先用 page.evaluate 只提取 #ProductList 的表头、分组、行 HTML 和行文本，再把这份局部快照交给 aiQuery 做语义提取。
- 这类方案的价值在于：既摆脱了固定列序的脆弱性，又把 AI 的上下文控制在产品表本身，不让它被整页其它数字干扰。
- 对“写操作”不能完全交给 aiQuery。像设置折扣这类动作，仍应由 Playwright 先读取当前表头，再按表头关键字动态定位列，再操作该行 input。

解决方案：

- 读取层：先抓局部 DOM 快照，再让 AI 只做“字段语义识别”，不要让 AI 兼任页面导航、业务计算。
- 写入层：优先保留 Playwright 的确定性交互，通过动态表头映射替代固定列索引。
- 校验层：AI 提取出来的行数据仍然必须回到公式校验，不能因为“去索引化”成功就默认业务正确。
- 如果页面在填值后会重渲染整行，要在轮询时重新抓当前行和当前 input，不要持续盯着旧 locator。

### 2.10 编辑页提交流程要做成“严格提交状态机”，不要做弱成功判断

- 本次验证下来，编辑页提交是否成功，不能靠页面跳转、按钮消失、URL 变化等弱信号判断。
- 真正可靠的成功标准是：点击“提交申请”后，没有新的业务拦截弹窗或错误提示，并且在限定时间内看到了“提交成功” toast。
- 这意味着提交 helper 不能只是 click 一下再 waitForTimeout，而是要明确观察提交结果，区分 success、blocking、timeout 三种状态。

解决方案：

- 提交主链路优先由 Playwright 控制，不要让 AI 接管提交是否成功这类关键状态判断。
- 把提交结果观察抽成统一函数，专门收集 toast、错误提示、弹窗文案，再返回标准化结果。
- 只有 success 才继续进入“我的申请”或详情页；blocking 和 timeout 都要立即报错或走有限重试，不允许假通过。

### 2.11 UNC 弹窗的正确处理顺序是“弹窗内关闭 -> 填 EDN 原因 -> 验证回写 -> 再提交”

- 本次已经确认，UNC 规则弹窗不是死路，正确业务路径是先关闭弹窗，再去填写“未下单EDN软件原因”，然后重新提交。
- 真正容易出问题的点不在“知道要填 EDN”，而在于脚本如果整页泛搜“关闭/确定”按钮，极容易点到弹窗外元素，导致卡在可点击等待里。
- 因此 UNC 处理必须限定在当前可见弹窗内部找按钮或关闭图标，关闭后还要验证 EDN 文本域确实写入成功，而不是 fill 过就算完。

解决方案：

- 先定位包含“UNC底座”“未下EDN软件原因”等关键字的当前可见弹窗，再在这个弹窗内部查找“关闭/知道了/确定”。
- 关闭后立刻回到编辑页表单，填写 EDN 原因，并读取 textarea 当前值确认内容已持久化。
- 只有完成“关闭 + 回写验证”后才允许第二次点击提交；否则应该立即报错，避免脚本静默卡住。

### 2.12 提交前要先清掉业务规则型阻塞项，而不是等提交时报错后再猜

- 本次已经验证，“服务商专供产品”属于明确的提交阻塞条件，只要产品信息中含有“服务商”字样，就可能在提交时被拦截。
- 如果目的是校验提交后详情页，而不是专门验证“服务商专供产品拦截规则”，那就应在提交前调用“删除服务商专供产品”动作，把页面先收敛到可提交状态。
- 这种处理不是绕过业务规则，而是把测试目标和业务前置条件对齐，避免在无关拦截上浪费调试时间。

解决方案：

- 在 actionSequence 里显式插入“删除服务商专供产品”这类提交前清理动作，不要把它埋进提交 helper 的黑盒兜底里。
- 清理后要同步刷新当前产品计划和编辑页价格基线，确保后续编辑页断言和详情页断言针对的是同一份提交内容。
- 对这类“明确不可提交”的规则，优先沉淀成可复用页面动作，而不是每个场景单独写临时修补代码。

### 2.13 提交后详情页必须按“本次提交单据”回捞，不能点最新一行兜底

- 本次验证过程中已经确认，如果提交后在“我的申请”里直接点最新一行，打开的未必就是本次刚提交的单据。
- 一旦详情页不是同一张单据，后续价格字段对比就失去意义，即使断言通过也是假结论。
- 因此提交成功后必须先记录本次提交时的业务机会名称或项目名称，再到“我的申请”里按同名记录打开详情。

解决方案：

- 提交前从编辑页读取并保存业务机会名称，作为后续详情页定位主键。
- 打开“我的申请”后，优先校验首条或目标条目的项目名称是否与本次提交记录一致，再执行点击。
- 禁止再使用“最新一行”“第一条记录”“有详情就进”这类弱定位策略替代同名单据回捞。

### 2.14 提交页尾部字段要允许“真实候选值回退”，不要把配置值当成绝对真值

- 本次在“服务主体”“服务所在地”等尾部字段上已经遇到过配置值与页面真实候选不一致的情况。
- 如果脚本死等配置值出现，会把问题误判成页面坏了；但真实原因可能只是当前模板下该选项不存在。
- 对这类业务下拉，脚本既要优先尝试配置值，也要保留“回退到页面首个真实可选项”的能力。

解决方案：

- 先按标签定位对应下拉，再优先选择配置中的目标值。
- 如果目标值不在当前下拉候选里，要把当前可见候选项记录下来，并按业务约定回退到首个真实可选项。
- 回退动作必须留日志，后续排查时才能分清“配置不匹配”和“页面定位失败”两类问题。

### 2.15 四场景流式验证要先跑通真实链路，再区分“业务差异”和“脚本缺陷”

- 本轮四大渠道场景复跑后已经确认，很多阻碍项并不是“脚本一定写错了”，而是不同业务场景下字段显示、输入要求、价格口径本来就不完全一致。
- 如果在没有业务判定前就直接修改脚本去消灭所有差异，很容易把正常业务分支误改成错误逻辑，反而越修越乱。
- 更稳的顺序是：先真实执行四个场景，记录每个场景的首个阻碍、页面截图、字段对比明细，再由业务方明确哪些是必须校验、哪些可以跳过、哪些属于业务正常分支。

解决方案：

- 对流式验证类场景，先把“阻碍项清单”和“不确定项清单”跑出来，不要一边跑一边默认所有差异都要修。
- 对每个阻碍项都附上阶段名、页面截图、字段对比文本，方便业务方快速判断“这是系统错误、脚本错误，还是正常业务差异”。
- 只有在业务方明确“这项应该一致/应该出现/应该填写”之后，再进入脚本修复；否则优先做 best-effort 收集或跳过策略设计。

### 2.16 无渠道场景下，服务主体为“原厂/客户自行实施”时缺少金额输入不是脚本错误

- 本轮已经由业务确认：无渠道场景下，服务主体如果只能选到“原厂”或“客户自行实施”，页面本来就不会出现 3 个金额输入框。
- 这说明“服务主体金额输入框不足”不能在所有场景下都当成硬失败；至少在无渠道场景、且服务主体属于这两个值时，这属于正常业务分支。
- 如果脚本继续强制要求这 3 个金额输入存在，就会把正常业务逻辑误判成自动化失败。

解决方案：

- 先读取当前服务主体文本，再决定是否要求金额输入框存在。
- 当服务主体为“原厂”或“客户自行实施”时，应跳过金额填写并继续后续流程，同时记录日志说明本次是按业务规则跳过。
- 只有当服务主体为其它可分摊金额的服务方时，才要求 3 个金额输入框出现，并做填写与回读校验。

### 2.17 价格对不上时，不要先假设公式错或系统错，要先把复核材料留全

- 本轮已经确认，如果脚本报出“价格清单”和“价格信息”不一致，但没有同时给出价格清单截图、价格信息截图、字段对比明细，业务方无法快速判定到底是公式写错、取值取错，还是系统本身展示有问题。
- 在这种情况下继续改公式或改读取逻辑，风险很高，因为你可能是在修一个其实并不存在的脚本问题。
- 因此，价格类差异在进入代码修复前，应先转成“可人工复核”的证据包。

解决方案：

- 发现价格字段不一致时，优先保留产品清单截图、价格信息区截图、字段对比明细、阶段名。
- 在没有业务复核结论前，不要默认把“价格差值”直接当成脚本 bug 去改。
- 业务复核后再分流：公式错则修 expected 计算，取值错则修读取逻辑，若业务确认页面本来如此则把该项改为跳过或局部断言。

### 2.18 审批流列表页要把“数据区”和“操作区”分开建模

- 本轮审批流脚本已经验证，订单中心列表不能简单当成一张平面表处理；很多页面实际上是“左侧数据表 + 右侧操作表”的分栏结构。
- 更稳的做法是分别抽取数据行和操作行，再通过相同的行序规则去绑定两边，而不是在同一行里同时找项目名称和操作按钮。
- 这类页面里，“我的申请 / 我的已办”通常取正序第一条作为最新数据，“我的待办”则要取倒序第一条作为最新数据；如果规则写反，极容易点错单据或点错操作。

解决方案：

- 列表 helper 要显式拆分为 dataRows 和 actionRows，不要把“项目名称存在”与“办理/编辑按钮存在”混在同一个 locator 里。
- 项目搜索结果判断要分别统计项目数据行数和项目操作行数，再按最大值判断是否真的命中目标单据。
- 取目标行时要把列表类型带进去，统一由一个 row picking 规则决定取 first 还是 last，避免每处调用自己猜。

### 2.19 总计/合计行必须在抽取层和期望计算层同时过滤

- 每个产品线最后一行带“总计”或“合计”的汇总行，不能参与 configured product 识别，也不能参与 expectedPriceInfo 计算。
- 这类行如果不在抽取层先过滤，后续 expected 计算、产品数校验、追加产品判断都容易被污染。
- 更稳的做法是：在 DOM 抽取层和 expected 计算入口同时加过滤，而不是等断言失败后临时补差。

### 2.20 现金点要先收敛到可计算状态

- 本轮已经验证，遇到“现金点=是”时，先把它收敛为“否”再做价格验证，链路更稳定。
- 这不是绕过逻辑，而是把场景先收敛到当前测试目标要覆盖的价格口径，避免引入额外计算分支。

### 2.21 赊销账期和资金占用费必须以真实保存结果和已确认口径为准

- 赊销相关字段不能只看脚本填了什么，还要看页面最终真实保存成了什么。
- 资金占用费类公式在未确认后台口径前，不能凭页面表象或脚本猜测直接改 expected。
- 更稳的顺序是：先验证账期是否真实保存，再查清系统到底按哪类出货价或哪一类基数计算，然后再补公式。

### 2.22 精度差异若确认不是脚本问题，就先按失败保留，不要自行放宽断言

- 本轮已经明确，精度问题如果确认不是脚本本身错误，应先按用例失败处理，不要私自放宽阈值或修改断言掩盖问题。
- 正确做法是保留对比明细、截图和阶段信息，再由研发和 PM 一起确认是接受该精度还是改系统口径。

### 2.23 追加产品后只等待新增产品稳定落表，不要强依赖旧产品同时可见

- 本轮已经验证，追加产品场景里真正需要确认的是“新追加的产品已经稳定落表”。
- 不必要求前面已存在的所有产品在当前 DOM 中同时可见，否则容易被折叠、虚拟滚动或局部重绘放大成假超时。
- 这类等待条件应收窄到当前动作真正要验证的最小结果。

### 2.24 单选字段切换要先判当前态，再做模糊匹配和结果校验

- 像“是否领料”这类单选字段，不能只依赖严格标签文本匹配，更不能点完就默认成功。
- 更稳的做法是：先判断目标选项是否已经选中；若未选中，再用适度放宽的文本匹配去点击；点击后再读一次真实状态确认切换成功。

### 2.25 需要同步到四套 baseline 的改动，应优先落在共享 action 或共享模板上

- 本轮已经验证，像“服务主体信息前移”“首次加品策略调整”这类要求，如果目标是四个渠道场景一起生效，优先修改共享的 `editInitialAdd`、共享 actionSequence 或基础模板定义，而不是分别在 4 套场景里平行补丁。
- 这样做的价值在于：一次修改就能自然扩散到无渠道、仅分销、仅首级、分销加首级，后续也更容易确认“是否已经同步到其他场景”。
- 如果一个变化只应该影响首步或某一个阶段，应优先改“该阶段的产品选择策略/动作定义”，而不是直接扩大所有后续步骤的产品集合。

解决方案：

- 先判断需求是“所有场景共用”还是“某个模板特例”。
- 只要是四场景共用，就先找共享场景定义、共享 action 或 base template 落点。
- 修改后优先单跑一个代表场景验证，再确认该共享改动是否自然覆盖其它场景。

### 2.26 为了支持后续删除/变更动作而新增产品时，优先增加“专用产品选择模式”，不要直接把后续所有步骤改成 all

- 本轮已经验证，如果只是为了让“删除服务商专供产品”这类后续动作有业务意义，不能粗暴把首次加品或后续所有步骤统一改成 `all`。
- 更稳的方式是：把目标产品追加到基础产品清单里，同时新增一个专用的选择模式，只在对应阶段取“原有主产品 + 新增目标产品”。
- 这样既能满足“首步必须带上该产品”的业务要求，又不会把原本不该提前出现的产品误带进后续断言和流程。

解决方案：

- 把新增产品追加在基础 `productPlans` 末尾，尽量不破坏已有按索引覆盖的前置产品配置。
- 新增语义化选择模式，例如“前两款主产品 + 服务商专供产品”，只给相关场景阶段使用。
- 同步更新该阶段标题和摘要，避免文案仍写“两款产品”造成误导。

### 2.27 场景标题前缀不要写死在基础模板里，否则会污染其它模板

- 本轮已经验证，如果把 `[仅分销]` 这类前缀直接写进基础模板的场景标题，后续变体模板再加自己的前缀时，容易出现 `[仅首级] [仅分销]` 这种串味标题。
- 标题前缀的职责应该属于模板变体，而不是基础场景定义本身。

解决方案：

- 基础场景标题保持无前缀、只表达业务动作和断言内容。
- 渠道标签统一在 `buildScenarioOptions` 或模板变体层追加。
- 如果要检查是否已污染其它模板，优先跑一个非基础模板的窄场景，看用例标题是否重复叠前缀。

### 2.28 非脚本问题导致的失败，不应中断同套后续用例执行

- 本轮已经明确，像系统业务拦截、口径待确认、金额精度差异这类“非脚本问题”，即使当前用例失败，也不应该阻断同一套场景后面的验证。
- 如果把整个 spec 设为 Playwright 的 `serial`，前一个失败会直接把后续测试标记为未执行，这会丢掉后续验证结果，不符合真实回归目标。

解决方案：

- 需要“共享一个 worker 顺序执行”，但又要“单条失败后继续跑后续用例”时，优先使用默认执行模式而不是 `serial`。
- 把“非脚本问题正常失败，但继续执行其它用例”当成显式设计要求，而不是事后人工补跑。
- 失败产物要照常保留，便于把脚本问题和系统问题拆开汇报。

### 2.29 稳定里程碑要同步做回退包，不要只靠口头记住“当前版本可回退”

- 本轮已经验证，四套 baseline 跑通后，如果不立即同步备份目录、README 和 zip，后续继续迭代时很容易丢失那个“当前稳定版本”的真实内容。
- 回退包不是单纯压缩一份代码，而是要连同“最新确认结果”和“本次纳入修正”一起记录下来，这样将来回切时才知道回到的是哪个状态。

解决方案：

- 每次稳定节点完成后，同步更新回退目录中的脚本文件、README 和同名 zip。
- README 要记录最近一次四套 baseline 的真实结果，而不是沿用旧结论。
- 对“已知保留失败但不视为脚本问题”的项，也要写进回退包说明，避免回切后重复误判。

### 2.30 下一审批人只能先解析成候选，真正执行人要以“谁的待办里有单据”为准

- 本轮审批流已经确认，状态文案里的审批人名称并不总是单人节点，也可能是并行审批节点，例如一个状态里同时出现多个姓名。
- 如果直接把整段括号内容当成单个用户去切身份，脚本会把真实并行审批误判成“人员配置缺失”或“待办没有数据”。
- 更稳的口径是：先从状态文案里解析出候选审批人列表，再逐个检查这些人的“我的待办”，谁的待办里真有这张单据，就由谁继续执行。

解决方案：

- 审批人名字先按中文逗号、英文逗号、顿号、斜杠等分隔符拆成候选集合。
- 对候选审批人优先轮询其“我的待办”；如果状态已经推进但任务分配有延迟，允许短时间等待，不要立刻判失败。
- 审批推进后的真实状态应以申请人的“我的申请”为准，不要用审批人的“我的已办”反推下一节点，因为已办列表可能刷新滞后。

### 2.31 审批意见输入框要按“底部真实控件”查找，不能只依赖命名 textarea

- 本轮审批页已验证，真正的必填“审批意见”不一定是普通 textarea，也可能是底部审批意见区域里的匿名 role=textbox 或 contenteditable 富文本控件。
- 如果脚本只找占位符明确的输入框，往往会填到上方普通备注框，却漏掉真正决定提交是否成功的底部意见框。
- 更稳的方式是先按“审批意见”所在行或区域定域，再从下往上扫描可编辑控件，优先命中最靠近底部动作按钮的真实输入点。

解决方案：

- 候选控件不仅要包含具名 textbox，还要包含 role=textbox 和 contenteditable=true 的可见节点。
- 候选筛选时要结合周边容器文本，如“审批意见”“请填写审批意见”，不要只看 placeholder 或 name。
- 对富文本类输入框，fill 失败时要回退到逐字输入，而不是直接判控件不可写。

### 2.32 菜单导航要做“点击后验明目标页，不对就回正”

- 本轮审批流里已经遇到过点击“我的待办”后实际落到“我的草稿”的情况，单纯依赖菜单点击结果并不可靠。
- 如果导航后不立刻校验当前 URL 或面包屑，脚本后续搜索为空时很难判断是列表真没数据，还是已经落到了错误页面。
- 更稳的做法是：先按菜单点击，再校验目标 URL 或关键列表输入框；如果发现不在目标列表，立刻用确定性直达 URL 回正。

解决方案：

- 为核心列表维护稳定的 URL 映射，例如“我的待办 / 我的已办 / 我的申请”各自的目标地址。
- 菜单点击后先等目标 URL；若超时，再走直达 URL 恢复，不要继续在错页上做搜索和点击。
- 进入列表后的第一页动作必须基于“项目名称输入框已可见”这类列表就绪信号，而不是把菜单点击完成当成页面已 ready。

### 2.33 审批链脚本要允许从非起始状态恢复，而不是假设每次都从首节点开始

- 本轮脚本已经验证，审批流脚本经常会在“驳回待提交”“召回待提交”甚至“流程结束”这些非起始状态下被重新执行。
- 如果脚本每次都假设当前单据一定停在首个审批节点，就会在复跑时走错链路，甚至把已结束单据当成脚本失败。
- 更稳的做法是先读取申请人视角的当前状态，再决定是继续审批、先重提恢复，还是直接因为业务状态已结束而停止。

解决方案：

- 用申请人的“我的申请”作为总控入口，先读取当前状态，再决定后续分支。
- 当状态为“驳回待提交”或“召回待提交”时，先执行编辑重提恢复，再继续审批链。
- 当状态已经是“流程结束”时，应直接输出明确业务态错误，避免把“单据已结束”误报成脚本故障。

### 2.34 长链路端到端脚本要用 test.step 显式分段，失败信息必须带阶段语义

- 本轮审批流是一个跨申请人、跨审批人、跨多次提交/召回的长链路，如果不做阶段切分，失败信息只会显示成某个深层 helper 报错，排查成本很高。
- 使用 test.step 把“首个审批人同意”“第二个审批人驳回”“申请人驳回后重提”“申请人召回后重提”“后续审批直至结束”这些关键阶段显式拆开后，定位会快很多。
- 这类分段不只是为了报告好看，更是为了让后续维护者快速区分：当前卡点是在列表找单、审批页提交、还是申请人恢复链路。

解决方案：

- 对每一段跨角色、跨页面、跨状态的关键动作都单独包一层 test.step。
- 阶段名要直接写业务动作和角色，不要只写“step1 / step2”。
- helper 抛错时要尽量附带当前列表、当前状态、目标按钮或目标字段，让报告能直接指向具体业务阶段。

### 2.35 “我的申请”区块标题必须按单据类型配置，不能直接复用菜单短标题

- 本轮 ECP 冒烟已经再次确认，“我的申请”页的区块标题和左侧菜单里的单据类型名称并不总是一致。
- 尤其是非特价下单，真实区块标题是“我的非特价下单”，如果脚本按“非特价下单”去定域，最终会退化成整页搜索，误命中特价、协议价或历史同名单据。
- 这类问题不会只影响“提交后回捞真实项目名”，还会继续污染申请人侧的状态读取、编辑重提、召回等后续动作。

解决方案：

- 为“我的申请 / 我的待办 / 我的已办”分别维护真实区块标题，不要偷懒共用一个短标题。
- 单据提交成功后的项目名回捞、申请人状态读取、编辑/召回动作都必须复用同一份区块作用域配置。
- 当前项目里，非特价下单在“我的申请”页应按“我的非特价下单”做作用域，而不是“非特价下单”。

### 2.36 同名项目复跑时，申请人侧状态解析必须优先命中“最新一条本人单据”

- 本轮审批流已经验证，只按项目名在“我的申请”里取第一条或当前状态，遇到历史同名单据时非常容易误判成“流程结束”或误跳到旧单据。
- 这类误判在长链路复跑时尤其常见，因为同一个项目名会连续经历提交、驳回重提、召回重提、再次审批等多轮状态变化。
- 更稳的口径不是“项目名命中即可”，而是“申请人正确、状态合法、最后修改时间最接近本次提交时间”的那一条。

解决方案：

- 申请人侧读取当前状态、下一审批人时，要优先走“最新申请人单据”解析逻辑，再回退到通用状态读取。
- 列表筛选条件至少要同时带项目名、申请人和最后修改时间窗口，不要只看项目名。
- 当项目名回捞失败但本次提交已经确认成功时，可以临时用本次提交时刻做兜底，但不要让兜底覆盖正常的最新行解析。

### 2.37 非特价下单的提交页和重提页要共享同一套页面修复动作

- 本轮已经验证，非特价下单不是“首次提交能过，重提自然也能过”的页面；驳回后重新提交、召回后重新提交时，项目所在区域、服务主体、诚信承诺等字段可能被系统回写或重新置空。
- 如果首次提交 helper 做了页面修复，但重提链路仍然走通用“点击编辑后直接提交”，脚本会在重提阶段重新掉回静默卡单。
- 另外，录制脚本只适合作为操作顺序参考，不足以直接当成稳定实现；像区域选择、服务主体选择、产品行定域这些点，必须回到 helper 层做确定性修复。

解决方案：

- 首次提交和编辑重提都要复用同一套页面修复逻辑，不要只在 submit helper 里修一次。
- 对非特价下单，至少要在修复动作里覆盖项目含镁光确认、项目所在区域、服务主体信息、诚信承诺这些易回写字段。
- 服务主体、服务所在地这类搜索型下拉框要按所在行定域，优先读当前真实值，不要用页级 locator 直接点第一个候选。

### 2.38 提交诊断里，搜索型下拉框要优先取真实选中值，不能把 placeholder 也算进“空值”

- 本轮非特价下单调试里已经遇到过一个典型误报：控件视觉上已经选中了“北京”，但 DOM 同时保留了“请选择项目所在区域”之类 placeholder 文本，导致脚本把它误判成必填未填。
- 这种误诊会把真正的业务阻塞点盖住，排查方向会被带偏到一个其实已经填好的字段上。
- 对 Ant Design 这类搜索型 select，真正应该优先读取的是可见的非 placeholder 文本，而不是把节点里的所有文本无差别拼接。

解决方案：

- 采集下拉框当前值时，优先过滤掉“请选择 / 请输入”这类 placeholder，再判断是否为空。
- 只有在没有任何真实候选文本时，才把 placeholder 当成“未填”的辅助信号。
- 页面诊断 helper 的目标是缩小根因范围，不要因为保守误报反而扩大噪音。

### 2.39 “待订单员发布合同”不是流程结束，而是一个必须切指定账号的隐式审批节点

- 本轮多个单据类型的审批链都再次证明，状态变成“待订单员发布合同”并不代表流程结束，而是需要切到订单员继续处理。
- 页面状态里显示的人名可能是“朱慧”，但当前测试账号映射实际要落到“朱惠/zhuh”；如果只按字面人名或全拼去切，很容易卡在 changeUser 页面。
- 这类节点如果不显式建规则，脚本会误把它当成“未解析出审批人”或“身份切换失败”。

解决方案：

- 状态命中“待订单员发布合同”时，审批人解析要优先走显式业务规则，不要只依赖括号里的人名。
- 用户显示名别名和登录账号前缀要分开维护；显示名可兼容“朱慧/朱惠”，实际登录应稳定回落到 zhuh。
- 这条规则应放在共享审批 helper，而不是散落在单个 spec 里写死。

### 2.40 要货时间字段不要写死成目标日期，只要页面已有有效值就应优先复用

- 本轮非特价下单已经验证，页面里的“项目要货时间”有时会自动保留系统当前可接受的日期，并不一定等于录制时看到的“下月 30 号”。
- 如果脚本把“必须改成目标日期”写成硬校验，即使页面已有合法日期，也会把业务正常状态误判成脚本失败。
- 这类字段真正要验证的是“必填项已有有效日期”，而不是“必须等于脚本理想值”。

解决方案：

- 进入页面后先读取当前日期值；若已存在合法日期格式，优先复用，不要强制重填。
- 只有字段为空、非法或业务明确要求改值时，才执行日期选择或输入动作。
- 对日期类必填项，优先做“存在性 + 合法格式”校验，再决定是否需要做值级断言。

## 3. 进一步收敛后的正向规范

### 3.1 AI 只用于局部区域提取，不做整页价格判断

- 先通过 page.evaluate 把目标字段所在区域裁出来，再把局部文本交给 aiQuery。
- 对 AI 提取结果增加业务公式校验，一旦和单价、数量、折扣等字段关系不成立，就立即判为失败。
- 如果某个字段在局部 AI 提取下仍然不稳定，就直接切换到 DOM 或 XPath 读取。

### 3.2 数量和价格输入始终按目标行定域

- 先通过型号、名称或其它业务主键锁定目标行，再在目标行内部定位数量输入框或价格输入框。
- 尽量使用 targetRow.locator(...) 这种“先缩小范围再取子元素”的方式，避免全局 XPath 误命中。
- 在填写前先打印目标行文本，确认命中的确实是要操作的产品。

### 3.3 以条件等待为主，sleep 只做补充

- 优先使用 waitFor、waitForLoadState、locator.waitFor 等条件等待，而不是只堆 sleep。
- 对列表查询场景，先等 loading 消失，再等目标行 visible，再执行点击或填值。
- sleep 只保留在界面动画、后端计算回填这类无法直接绑定明确条件的短暂过渡阶段。

### 3.4 0 值字段使用显式数值判断

- 所有数值字段统一使用 Number.isFinite、value !== null、value !== undefined 之类的显式判断方式。
- 在字段读取函数里就完成类型转换，保证后续流程拿到的是明确的 number，而不是字符串或空值。
- 在价格校验前打印字段类型和值，第一时间发现 0 被误判的问题。

### 3.5 修改和执行始终锁定工作区主文件

- 每次修改前先确认 VS Code 当前打开文件和运行命令所在目录是否一致。
- 在脚本顶部、日志输出或文档里明确主维护文件路径，避免同名文件混淆。
- 运行脚本时固定在项目根目录执行，降低误改副本或误跑错误入口的概率。

### 3.6 点击后要验证真实聚焦和真实状态变化

- 点击后立即验证 document.activeElement 是否已经切到目标 input，或者检查输入框状态是否真的变化。
- 对容易被遮挡的控件，采用“普通点击 -> force click -> 原生 focus/click”的分级兜底策略。
- 如果业务逻辑依赖 focus、input、change、blur 事件链，就要显式补齐这些事件。

### 3.7 关键恢复主链路使用确定性控制流

- 页面恢复优先使用 Playwright 的确定性控制流，例如：当前页检测 -> 目标 URL 打开 -> 草稿页搜索并点编辑 -> 多标签页回收。
- aiAction 只适合做非关键、弱结构、低风险的补充动作，不适合做关键状态机的主控制器。
- 任何恢复逻辑最终都必须以可验证状态收口，例如确认“基本信息”“产品清单”“价格信息”三个区域都已回到编辑页。

### 3.8 aiAssert 只做视觉补充断言

- 先用 Playwright 校验底层值和业务公式，再用 aiAssert 校验页面视觉呈现，形成“双层断言”。
- aiAssert 的提示词应引用配置和公式算出的期望值，而不是直接复用页面刚读出来的当前值。
- 对金额、折扣这类字段，提示词里要允许 35 和 35.00 这类等值展示格式，减少显示格式差异造成的误报。

## 4. 后续验证更多价格字段时的推荐方法

### 4.1 先给字段分层，再决定技术方案

- 主表输入框字段：优先 XPath 或 DOM 直接读。
- 弹窗表格字段：先定位到目标行，再在行内取值。
- 汇总区字段：先限定到某个 DOM 区域，再做 AI 提取。
- 文案型、说明型、弱结构字段：可以考虑 AI，但要尽量缩小上下文。

### 4.2 每新增一个字段，都同时准备三样东西

- 字段读取方式。
- 字段合法性校验。
- 该字段参与的业务计算关系。

例如后续如果新增“标准价”“折扣额”“未税价”“税额”，就不应只提取一个数字，而应同时写清楚它和其它字段的计算关系。

### 4.3 推荐的验证顺序

1. 先确认字段在页面上属于哪一块区域。
2. 再判断该字段更适合 XPath 直读还是 AI 局部提取。
3. 先打印该字段的原始文本或原始 inputValue。
4. 再做数值转换。
5. 最后做跨字段公式校验。

### 4.4 推荐的调试顺序

1. 先验证页面交互是否真正完成，例如点击、搜索、填值、关闭弹窗。
2. 再验证字段提取是否正确。
3. 最后验证价格公式是否成立。

如果一开始就把页面操作、字段提取、业务校验混在一起排查，定位会非常慢。

## 5. 已验证值得固化的通用能力

- 统一的数字读取函数：负责读取、去逗号、转数字、校验。
- 统一的区域快照函数：负责抓取某个 DOM 节点下的文本和 input 值。
- 统一的局部 AI 提取函数：负责只对指定区域文本做 aiQuery。
- 统一的价格校验函数：负责根据业务公式判断是否通过。
- 统一的点击兜底函数：负责文本点击、XPath 点击、原生事件点击的降级处理。
- 统一的提交结果观察函数：负责采集提交成功 toast、错误提示、弹窗文案，并返回 success/blocking/timeout 标准状态。
- 统一的弹窗定域关闭函数：负责先锁定当前可见弹窗，再在弹窗内部点击“关闭/知道了/确定”或右上角关闭图标。
- 统一的提交前业务清理函数：负责删除服务商专供产品、补齐必要尾部字段、执行 AI 合规检查等提交前收口动作。
- 统一的确定性恢复函数：负责把当前 page 恢复到目标业务编辑态，并在失败时给出明确页面状态。
- 统一的重渲染后重取 locator 函数：负责在表格整行刷新后重新拿到当前 input，避免旧句柄失效。
- 统一的视觉断言提示词生成函数：负责把配置和公式期望值转成 aiAssert 提示词，而不是直接复用页面现值。
- 统一的审批人候选解析与真实待办确认函数：负责把状态文案中的并行审批人拆分成候选集合，并通过“我的待办”真实归属确认当前执行人。
- 统一的分栏列表行绑定函数：负责把数据区行和操作区行按列表类型绑定到同一条业务记录上。
- 统一的审批页底部意见框定位函数：负责按审批意见区域、底部顺序和富文本候选控件定位真实必填框。

这些能力一旦稳定，后面新增字段时就不需要每次都从零写一遍。

## 6. 本轮最典型的失败警示

- 不要把非脚本问题伪装成通过：像金额精度差、业务口径待确认这类问题，应保留失败结果和证据，不要私自放宽断言。
- 不要把整套 spec 设成 `serial` 后再指望“失败也继续跑”：这会直接让后续用例被跳过，丢掉完整回归结果。
- 不要为了让后续删除/变更动作有意义，就把所有后续步骤都扩大成 `all`：应增加专用产品选择模式，只影响对应阶段。
- 不要把渠道标题前缀写死在基础模板：否则其它模板会被污染，出现重复前缀或错误场景标签。
- 不要只更新代码，不更新回退包：稳定节点如果不立即同步 README 和 zip，后续很难准确回切到“当时真正稳定的版本”。

## 7. 下一轮使用建议

- 扩字段时一次只新增 1 到 2 个字段，不要一口气改太多。
- 每新增一个字段，就立刻打印中间值并做一次公式验证。
- 优先扩展结构最稳定、业务关系最清晰的字段。
- 如果某个字段 AI 反复不准，不要硬扛，应尽快改为 DOM 或 XPath 读取。
- 如果确实只能用 AI，就先把页面区域缩小，再让 AI 做提取。
- 后续继续沿用“页面交互 -> 字段提取 -> 业务校验”的分层方法，不要退回到“整页 AI 一次性提取全部数据”的做法。
