# 高质量提问模板

本文档用于沉淀“如何向 GitHub Copilot / 自动化脚本生成助手提问”，目标是让后续生成脚本时更精准、回归次数更少、结果更符合真实业务预期。

建议在每次提出新的脚本生成、脚本修复、场景扩展、失败排查需求前，先快速阅读本文件，再按模板组织问题。

## 0. 核心原则

- 先给目标，再给约束，再给成功标准，不要只给一个笼统诉求。
- 先说“什么才算成功”，再说“怎么实现”，这样脚本不会走偏成弱判定或假通过。
- 先说“绝对不能怎么做”，比只说“希望怎么做”更能防止生成错误路径。
- 先给真实业务规则，再让脚本落地；不要让模型仅凭页面现象猜业务。
- 先指定当前修改锚点，例如已有用例、已有 helper、已有失败场景，不要让模型从整仓库重新猜入口。
- 先说明是否必须共用当前编辑页、复用当前 helper 或沿用当前动作链，不要让模型自行改成切页或重开新流程。
- 先明确这是“脚本阻碍”还是“业务差异/精度差异”排查，避免模型把两类问题混着修。
- 先给出口径边界，例如“若确认不是脚本问题，不要自行放宽精度断言”，这样模型不会擅自改判定标准。
- 先指定验证范围，例如先单跑还是直接全回归，避免一上来扩大验证面导致定位变慢。
- 先指定修复扩散顺序，例如“先修第 1 点，确认无误后再把同样思路推广到另外 3 个场景”。

## 1. 为什么有些提问会让脚本更准

高质量提问最重要的，不是说得多，而是说得“可执行”。

下面这几类信息，对脚本质量提升最大：

- 目标锚点：明确是哪个文件、哪个场景、哪个 helper、哪个失败链路。
- 成功判定：明确什么现象出现才算成功，什么现象出现就算失败。
- 业务限制：明确不能使用哪些弱策略、哪些入口无效、哪些逻辑必须保持一致。
- 真实处理路径：明确遇到某个弹窗、某个规则、某个拦截时，人工正确操作是什么。
- 口径边界：明确哪些问题属于脚本阻碍，哪些属于业务差异或精度差异，以及对应怎么处理。
- 扩散规则：明确修复后是先回归单场景，还是确认后同步推广到其它场景。
- 验证策略：明确先单场景验证，还是直接整组回归。

## 2. 提问前的速查清单

在发起需求前，尽量先准备这些信息：

- 当前要改的是哪个文件。
- 当前要改的是哪个用例或哪个 helper。
- 当前脚本的目标行为是什么。
- 成功标准是什么。
- 不允许的实现方式是什么。
- 已知失败点是什么。
- 已知业务规则是什么。
- 是否要求共用当前编辑页或当前会话，不允许反复切页、切用户、开新页。
- 是否存在绝对不能参与计算的行或字段，例如“总计/合计行”。
- 是否存在需要先归一化的业务值，例如“现金点=是”时先改成“否”。
- 精度差异若确认不是脚本问题时，是保留失败，还是允许临时降级为收集信息。
- 如果系统公式口径未确认，是否要求先查真实口径，再改 expected 计算。
- 如果已有报错，核心报错文案是什么。
- 希望先执行哪一条验证命令。
- 修改时优先复用现有逻辑，还是允许新增独立逻辑。

如果上述 10 项里至少能给出 6 到 8 项，脚本通常会明显更贴近你的真实诉求。

## 3. 最推荐的提问结构

建议以后尽量按下面 6 段组织你的问题。

### 3.1 先给任务目标

直接说清楚你要改什么，不要让模型自己猜。

推荐表达：

- 请修改某个现有用例，不要新建脚本。
- 请在某个 helper 上修复这条提交链。
- 请把某个已通过 baseline 扩成编辑页 + 详情页双端校验。

### 3.2 再给修改锚点

明确文件和场景，可以大幅减少搜索和误改。

推荐表达：

- 目标文件是某个 spec。
- 基于某个已通过场景继续改。
- 优先修改某个 helper，不要平行再造一套流程。

### 3.3 再给成功标准

这是最关键的一段。

推荐表达：

- 点击提交后 3 秒内必须出现“提交成功” toast。
- 期间不能出现任何阻塞弹窗或错误提示。
- 提交后必须进入“我的申请”中的同名单据详情页。
- 价格对比必须基于同一张单据，不允许按最新一行兜底。

### 3.4 再给强约束和禁止项

禁止项可以防止脚本生成成“能跑但不对”的版本。

推荐表达：

- 不能按最新一行进入详情页。
- 不能靠 URL 变化判断提交成功。
- 不能跳过业务规则直接 force 通过。
- 不能新建独立脚本，必须复用现有框架。

### 3.5 再给真实业务规则

这是通过率提升最快的信息。

推荐表达：

- 如果出现 UNC 弹窗，先关闭，再填写未下单 EDN 软件原因，再重新提交。
- 如果产品中包含服务商专供产品，提交前要先执行删除服务商专供产品。
- 某字段配置值在页面可能不存在，此时允许回退到首个真实可选项。

### 3.6 再给差异归类和放大策略

这是这轮对话里最能提升脚本质量的一段补充信息。

推荐表达：

- 当前问题先按“脚本阻碍”处理，不要把精度差异一起改掉。
- 如果确认不是脚本问题，先按用例失败保留，不要自行放宽阈值。
- 先只修这一处并单跑这一条，确认无误后，再把同样思路同步到其它场景。
- 如果系统真实口径还不清楚，先查清系统到底按什么算，再补 expected 公式。

### 3.7 最后给验证要求

推荐表达：

- 先只跑这一条场景。
- 通过后再跑另外 3 条回归。
- 如果单跑失败，先读取最新 error-context 和 screenshot，不要直接大改。

## 4. 哪些提问方式不够好

下面这些提问不是不能做，而是会显著增加试错成本：

- “帮我修一下这个脚本。”
- “再试一下。”
- “把它改成双端校验。”
- “还是不行，你再看看。”
- “我想让它更稳定一点。”

这些说法的问题是：

- 没有目标锚点。
- 没有成功标准。
- 没有业务规则。
- 没有说明什么叫“修好”。

更好的方式是把这几句改写成：

- 请修改哪个文件里的哪个场景。
- 当前失败点是什么。
- 真实人工操作路径是什么。
- 哪种结果才算成功。

## 5. 最常用的高质量提问模板

下面这些模板可以直接复制后替换内容。

### 5.1 模板一：修改现有场景

```md
请修改 [目标文件] 里的 [目标场景]，不要新建独立脚本。

目标：
- [你希望实现的行为]

当前前提：
- 已通过 baseline：[已通过的基础场景]
- 当前失败点：[当前报错或卡住的位置]
- 当前真实页面入口：[草稿页 / 编辑页 / 我的申请 / 详情页]

成功标准：
- [成功标准 1]
- [成功标准 2]
- [成功标准 3]

强约束：
- 不允许：[禁止项 1]
- 不允许：[禁止项 2]
- 必须：[必须满足的约束]

已知业务规则：
- [业务规则 1]
- [业务规则 2]

执行要求：
- 优先修改：[现有 helper / 现有 actionSequence / 现有 spec]
- 先只跑：[单场景 grep]
- 如果失败：[先看 error-context / screenshot / trace]
```

### 5.2 模板二：修复提交链

```md
请修复 [目标文件/目标 helper] 的提交流程。

当前问题：
- 点击提交后会出现：[弹窗/提示/拦截文案]
- 当前脚本错误地把 [弱信号] 当成成功

真实业务规则：
- 如果出现 [规则 A]，正确操作是：[人工处理步骤]
- 如果出现 [规则 B]，正确操作是：[人工处理步骤]

成功判定：
- 只有在 [限定时间] 内出现 [成功 toast 文案]，且没有新的阻塞提示，才算提交成功

禁止项：
- 不能用 [URL 变化 / 页面跳转 / 按钮消失] 代替成功判定
- 不能忽略弹窗继续往后跑

验证方式：
- 先单跑：[命令]
- 再决定是否放大回归
```

### 5.3 模板三：扩展成双端校验

```md
请把 [当前单端场景] 扩成“编辑页 + 提交后详情页”双端校验。

修改锚点：
- 文件：[目标 spec]
- 基于场景：[当前已通过 baseline]

详情页约束：
- 必须从 [我的申请] 中按 [项目名称/业务机会名称] 打开同一张单据
- 不能按最新一行兜底

成功标准：
- 编辑页价格断言通过
- 提交成功
- 打开的详情页与本次提交单据一致
- 详情页价格断言通过

验证要求：
- 先只跑这个场景
- 通过后再回归其它场景
```

### 5.4 模板四：提供关键业务提示后继续修复

```md
补充一个关键业务规则，请基于这个规则继续修复当前脚本，不要回退到弱判定。

新增业务规则：
- [规则内容]

这条规则影响的步骤：
- [提交前 / 提交时 / 详情页打开时 / 尾部字段选择时]

请你：
- 按这条规则修改现有实现
- 修改后先单跑 [目标场景]
- 如果仍失败，优先读取最新错误产物再继续修
```

### 5.5 模板五：区分脚本阻碍和业务差异

```md
请先把当前问题分成“脚本阻碍”和“业务差异”两类处理，不要混着修。

当前现象：
- [失败文案 / 页面现象 / 字段差异]

我的判断边界：
- 这次优先处理：[脚本阻碍 / 业务差异]
- 如果确认不是脚本问题：[保留失败 / 只留证据 / 不要放宽断言]

成功标准：
- 本轮至少要消除的脚本阻碍是：[具体阻碍]
- 本轮不处理的业务差异是：[具体差异]

验证方式：
- 先只跑：[单场景]
- 确认阻碍消失后，再决定是否全量回归
```

### 5.6 模板六：先修一个点，再扩到其它场景

```md
请先只修 [第一个明确问题]，不要同时大改其它逻辑。

修改锚点：
- 文件：[目标文件]
- 失败点：[具体函数 / 具体步骤 / 具体报错]

执行顺序：
- 第一步：只修这一处
- 第二步：单跑 [目标场景] 验证
- 第三步：如果通过，再把同样方法推广到 [其它场景列表]

禁止项：
- 不要在第一步顺手放宽其它断言
- 不要在未验证前同时修改多个场景的实现
```

## 6. 本轮已验证有效的补充提示

下面这些表达，已经在本轮对话里证明能显著提升脚本生成和修复质量：

- 直接给出当前最可能的控制点，例如“先看 waitForConfiguredProductModels 和它的调用方”，可以显著减少无关搜索。
- 明确说“共用一个编辑页，不要反复切用户后打开新编辑页”，能帮助模型保住稳定状态机。
- 明确说“总计/合计行绝对不能参与计算”“现金点遇到是时先改成否”这类硬业务规则，能减少脚本自己猜口径。
- 明确说“如果是脚本问题请修复；如果不是，就按真实失败保留，不要改断言口径”，能避免模型把业务问题误修成脚本问题。
- 明确说“只要不是脚本问题，就正常失败并继续执行后面的测试用例”，能避免模型沿用 `serial` 语义导致后续用例被跳过。
- 明确说“请改共享 flow / 共享 action，不要分别在 4 个场景里复制修改”，更容易命中真正的共享落点。
- 明确说“第一次添加产品时增加这个型号，确保后续删除这个产品有意义；所有场景的第一步都要增加它”，能把新增数据限制在正确阶段，而不是放大到所有后续步骤。
- 明确说“改完后同步更新回退包 zip 和 README”，模型才会把可回退资产一起维护，而不是只改代码。

这些表达之所以有效，是因为它们同时给了模型 4 类关键信息：

- 是否需要继续执行后续验证。
- 改动是局部修复还是跨场景同步。
- 新增数据的业务目的是什么。
- 代码改完后是否还要同步维护回退资产。

## 7. 很典型的低质量补充方式警示

- “你再看看”这类补充太弱，既没有说明问题归属，也没有给出口径边界。
- 只说“把它加进去”而不说明新增数据应该出现在哪个阶段，容易让模型把改动过度扩散到所有步骤。
- 只说“都同步一下”而不说明是改共享流还是改各场景特例，容易让实现落到重复补丁上。
- 只说“我想保留当前版本”而不点明回退目录、zip 和 README，容易出现代码更新了但回退包没同步。

## 8. 如果你想让我一次做得更贴近预期，最好额外补充这些信息

下面这些信息不是每次都必须给，但只要能给，命中率会明显提升：

- 当前目标是“验证价格逻辑”还是“验证提交流程本身”。
- 当前问题是否已经人工判定为“脚本阻碍”还是“业务差异/系统口径待确认”。
- 失败后最优先看的产物是哪一个，例如 screenshot、error-context、trace、helper log。
- 如果失败后仍要继续执行后续用例，请明确说明哪些失败属于“保留失败但继续跑”。
- 如果新增测试数据只是为了支撑后续某条用例，请明确它应该出现在哪个阶段。
- 如果修复一处后需要推广到其它场景，哪些场景要同步，哪些场景先不要动。
- 如果你希望改完后还能随时回退，请明确指出要同步更新哪个回退目录、zip 和 README。

## 9. 推荐的对话节奏

如果你希望效率更高，建议按下面节奏和我配合：

1. 第一轮先给目标场景、成功标准、禁止项、业务规则。
2. 第二轮如果我跑失败了，再补充人工真实处理路径，或补充“这属于脚本阻碍还是业务差异”。
3. 第三轮只给新的业务提示、口径边界或新的错误现象，不要重复整段上下文。
4. 如果你已经知道修复扩散顺序，例如“先修一个点，再推广到其它场景”，请直接说出来。
5. 如果你已经人工验证过页面行为，请优先告诉我“人是怎么操作成功的”。

这种对话方式通常比“先让我自由摸索，再一点点纠偏”更快。

## 10. 一句话版提问公式

如果你时间很紧，可以至少按这一句来提问：

“请修改 [文件/场景]，目标是 [目标行为]；成功标准是 [成功标准]；不允许 [禁止项]；已知业务规则是 [业务规则]；当前优先处理 [脚本阻碍/业务差异]；如果不是脚本问题则 [保留失败/继续执行后续用例]；先只跑 [验证范围]。”

## 11. 后续维护建议

- 本文件后续可以持续补充“高质量提问案例”。
- 每次只要发现一句关键业务提示直接改变了脚本实现方向，就值得把这句话沉淀进来。
- 后续如果出现新的高频场景，例如“新增字段验证提问模板”“报错排查提问模板”“详情页一致性提问模板”，都可以继续往本文件追加。

## 12. 建议执行方式

- 每次正式提问前，先快速阅读本文件第 0、2、5 节。
- 如果是新场景，优先复制第 5 节模板后填写。
- 如果是失败后补充信息，优先复制第 5.4 节模板。

这样能让问题更像“可执行需求”，而不是“开放式聊天”，脚本通常会更准，执行通过率也更高。
