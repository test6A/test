# 测试用例生成平台专业评估报告（全量基线）

## 一、管理结论

本次以 `PC马币下单项目-测试导图.mm` 作为需求金标，对平台生成的 TC-001～TC-102 共 102 条测试用例进行正文级审计。本轮不剔除 UI，也不剔除 CES。

> **推荐向管理层汇报的主指标：严格加权有效覆盖率 32.0%。**  
> 严格完整覆盖率只有 **11.8%**；另有 **40.4%** 仅部分覆盖、**7.2%** 错误覆盖、**40.6%** 遗漏。

平台产物的结论评级：**C 级，需整改；不建议直接作为正式回归集或发布准入依据。**

平台的优势是结构化产出完整、生成速度快、能补充权限、异常降级和数据层风险；核心问题是需求忠实度、原子性、跨角色/跨系统闭环、唯一预期和可执行数据不足。最危险的不是“没写”，而是把错误实现或未确认裁决写成正确预期。

| 质量维度 | 评级 | 管理判断 |
|---|---|---|
| 结构化完整性 | A | 字段和步骤齐全 |
| 需求覆盖与闭环 | D | 加权32.0%，CES/合同/PO结构性缺失 |
| 需求正确性 | D | 12个Case含硬冲突，触发不通过门禁 |
| 可执行性 | C | 大量复合/弱预期，缺数值、接口和故障注入参数 |
| 可追溯性 | D | 无稳定Requirement ID，内部171口径含重复 |
| 风险发散能力 | B | 权限、降级、异常扩展有价值 |
| **综合** | **C** | **只适合作为人工评审草稿** |

## 二、覆盖率结果

### 2.1 分母与计算规则

人工导图共有 475 个原始叶子，其中 12 个纯空白、7 个备注/建议/疑问。为避免把无预期内容当成需求，本报告采用 456 个有效人工原子检查点作为主分母；UI 和 CES 检查点全部保留。

判定与权重：

- 完整：同页面/系统、同角色/状态、同规则，有操作和唯一预期，权重 1；
- 部分：主题正确但缺字段、条件、角色、数值、时点或独立断言，权重 0.5；
- 错误：平台正式预期与人工基线相反，权重 0；
- 遗漏：无同上下文证据，权重 0。

### 2.2 总体覆盖率

| 分类 | 数量 | 占456比例 | 说明 |
|---|---:|---:|---|
| 完整覆盖 | 54 | 11.8% | 可直接支撑该原子检查点 |
| 部分覆盖 | 184 | 40.4% | 只能证明主题或部分字段被覆盖 |
| 错误覆盖 | 33 | 7.2% | 存在明确反向预期，按0分计 |
| 遗漏 | 185 | 40.6% | 无同页面、同角色、同规则证据 |
| **合计** | **456** | **100.0%** |  |

```text
严格加权有效覆盖率
=（完整 + 0.5 × 部分）÷ 有效人工检查点
=（54 + 0.5 × 184）÷ 456
= 146 ÷ 456
= 32.0%
```

辅助指标：

- 严格完整覆盖率：54 / 456 = **11.8%**；
- 非错误证据命中率：（54 + 184）/456 = **52.2%**；
- 错误或遗漏占比：（33 + 185）/456 = **47.8%**；
- 原始 475 口径：19 个无效叶子按0分保留，严格加权为 146/475 = **30.7%**。

早期只做主题相似度时得到的 46.1% 是未经过页面、角色和规则门禁的自动候选值；正文逐项复核后降为 32.0%，下降 14.1 个百分点。**102 条 Case、171 个源场景、442 条预期断言都不是覆盖率分母。**

## 三、102 条用例本身的质量

### 3.1 数量和结构

- TC-001～TC-102 连续、唯一、无缺号；`manifest.json` 与单文件数量均为102。
- `cases.md` 是102个单文件的汇总镜像，不能再次计数。
- 102/102 有前置条件、测试数据条件、最终预期、来源和测试步骤。
- 共有339个步骤、442条预期子断言，平均3.32步、4.33条预期/用例；无空步骤和空断言。

形式结构是平台最明显的优点，但结构完整不等于业务可执行。

### 3.2 平台内部覆盖自证存在口径膨胀

`coverage-map.json` 的171项由116个 independent、18个 merged、37个 duplicate 组成，重复项占21.6%。`manifest.json` 实际只记录141个脑图节点链接；多出的30项来自 duplicate。平台内部“171/171已覆盖”只是源脑图到Case的链接闭合，不是171个独立需求，更不是人工456点的覆盖。

### 3.3 可执行性问题

| 问题 | 审计结果 |
|---|---:|
| 所有类型均标为 `ui` | 102/102；至少22条明显属于API、任务、DB、消息、故障注入或人工测试 |
| 稳定 Requirement ID | 0/102 |
| 优先级、环境、后置清理 | 0/102 |
| 测试数据条件写“无” | 8/102 |
| 绑定多个脑图节点 | 23/102（22.5%） |
| 含复合断言 | 58/102（56.9%） |
| 带差异标记 | 18/102（17.6%） |
| 硬编码账号 | 23/102 |
| 完整的“USD原金额＋汇率＋期望MYR值”数值 oracle | 0/102 |

`diff-report.md` 关联34个Case，但只有18个Case正文带“差异标记”，16个关联Case漏标，漏标率47.1%；差异追踪尚未真正闭环。

TC-024、TC-076、TC-090、TC-092/093、TC-095、TC-099、TC-101、TC-075 等缺接口参数、数据表/SQL、故障注入、恢复清理、CES schema/ACK、浏览器/设备版本或明确数值，无法按当前文本直接稳定执行。

另有19个Case含明显的需求外扩展断言，例如接口权限、分享购物车、缓存/数据库降级、AI识别失败默认USD、浏览器兼容等。扩展可以保留为风险补充，但扩展断言不进入人工需求覆盖分子；同一Case中与基线一致的其他原子断言仍单独计分。

## 四、平台做得好的地方

1. **产物结构化程度高。** Case ID、前置、数据、步骤、逐步预期和来源字段齐全，便于进入后续评审流程。
2. **汇率更新和邮件规则相对较强。** 首次同步、超阈值待生效、到期生效、≤阈值取消、失败重试、收件人优先级和邮件正文等有较清晰步骤。
3. **有工程风险发散能力。** 补充了接口权限、无效汇率过滤、缓存/数据库降级、失败副作用、跨渠道越权等人工导图未完全展开的场景。
4. **追踪文件无坏链。** coverage-map中的Case ID和步骤号均有效；问题在于追踪到的是平台自己的源场景，而非人工需求金标。

## 五、核心欠缺点

### 5.1 需求与当前实现冲突时，平台选错了事实来源

用例目录的 `diff-report.md` 明确用 q1～q12 把部分“当前实现”裁决为目标规则，并宣称“无待确认差异”。本次人工导图被指定为需求基线，因此默认精度4、无免责声明、国家可编辑、审计无前后值、提交时才锁定等必须判错误。

若 q1～q12 确实有正式变更审批，应先更新需求金标，再重算覆盖；不能让平台在需求未更新时用代码现状覆盖需求。

### 5.2 复合句过度压缩人工原子点

“商品、服务、税、运费、返利、现金折扣和总额均按RM展示”不能等价于7个字段都被完整验证。每个字段还要有来源金额、换算公式、币种符号、舍入精度、锁定时点和变化后的联动。56.9%的Case含复合断言，导致执行、失败定位和覆盖证明都不可靠。

### 5.3 跨角色、跨页面、跨系统闭环薄弱

- 两条端到端主链只提到泛化审批和抛CES，缺受控、法务、销售、CES商务、订单员逐角色状态。
- Search Order有效94点只完整覆盖6点；合同详情39点全部遗漏。
- CES五个有效模块均为0%；TC-003没有CES步骤，TC-095只验证optional兼容。
- 人工15个导出字段点没有PO逐字段断言。
- 审批22点没有角色矩阵，命中项全部只能部分覆盖。

### 5.4 金额项目缺少可计算预期

102条Case中没有一条同时给出USD原金额、明确汇率和期望MYR结果。大量预期只是“正确”“一致”“按RM展示”，不能验证公式、精度、舍入尾差和锁定快照。

### 5.5 缺少需求追踪矩阵

平台没有 `Requirement ID ↔ Case ID ↔ Step/Assertion ID` 双向关系，无法稳定回答：哪个需求被哪一个具体预期覆盖、是完整还是部分、需求变更影响哪些Case、哪些Case是扩展或重复。

## 六、明确错误与高风险用例

含硬冲突的12个唯一Case：

`TC-001、TC-002、TC-005、TC-009、TC-011、TC-012、TC-014、TC-017、TC-022、TC-041、TC-046、TC-048`，占11.8%。

主要冲突：

- 默认精度4、前台按配置精度，反向于默认2和前台固定2位；
- 三个数值字段越界后拒绝，反向于钳制到边界；
- Admin无免责声明、前台不展示，反向于中英文必填、展示和订单快照；
- 编辑国家可改，反向于国家/编码/结算币种只读；
- 审计不记录前后值，反向于完整审计要求；
- 确认页只作参考、提交才锁定且允许切币，反向于进入确认页锁定并继承只读币种。

上述反向规则的潜在影响范围至少涉及56个有效人工检查点。四态统计坚持“同页面直接冲突”门禁，只把33点计为错误；其余跨页面传播风险不机械标错，而是按实际证据列为部分或遗漏。与此同时，TC-014与TC-039/046/064在免责声明上内部矛盾，TC-005/041与TC-012来源中的默认2矛盾，TC-046与TC-047在锁定语义上矛盾。

## 七、重点遗漏

### P0

- CES商务待确认/已确认、订单员待审批/已审批、PO完整字段链；
- 合同详情39个字段与快照检查点；
- 受控/法务/销售 × 移动端/后台待办 × 金额字段矩阵；
- 固定2位、确认页锁定和币种只读的正确口径；
- 免责声明中英文配置、语言切换、灰字、订单快照和后台变更后保持；
- 组合包下单品价格分摊与舍入尾差；
- PO的Unit Price、Total Amount、Sub total、返利、现金折扣、Freight、TOTALAMOUNT、币种。

### P1

- Admin国家/币种搜索、大小写、单选、高亮、清空、联动复位；
- 数字字段非数字、粘贴、步进和钳制；取消/X、防连点、精确确认文案；
- 产品/购物车/结算停留、刷新、前进后退的汇率更新边界；
- Re-order的MYR/USD、配置启停和新旧汇率分支；
- 分页9/10/11条、页码省略和page-size切换。

### P2

- 并发改配置、重复提交、汇率提交瞬间变化、服务恢复与幂等；
- 环境、账号、浏览器、设备、接口和数据准备参数化；
- 长文案、不同分辨率及可访问性。

## 八、优化建议

### P0：先解决“生成错”和“无法证明覆盖”

1. 建立来源优先级：正式需求/已审批变更 > 产品确认 > 设计/接口 > 当前代码 > 模型推断。
2. PRD与代码冲突时输出待确认项；在得到审批证据前，禁止生成确定预期。
3. 先原子化需求并生成稳定Requirement ID，再输出 `Requirement ↔ Case ↔ Assertion` 双向追踪。
4. 冲突自检必须识别默认值、范围、越界行为、可编辑性、是否展示、舍入精度和锁定时点。
5. 单条Case或断言映射超过5个需求点时，强制拆成逐字段、逐角色、逐状态断言。

### P1：提升业务闭环和可执行性

1. 建立“页面 × 金额字段”“角色 × 审批状态”“配置状态 × 订单生命周期”“汇率变化时点 × 页面行为”四类矩阵。
2. 用状态机生成产品→购物车→结算→确认→成功→订单/合同详情→审批→CES→PO闭环。
3. 金额用例必须生成可计算数据：USD原值、汇率、计算公式、舍入方式、预期MYR值。
4. 按UI/API/服务/DB/消息/下游/人工测试正确分类，并补齐接口、SQL、故障注入、观察点和清理步骤。
5. “正确/正常/一致/或”不能作为唯一预期；必须给确定字段和值。

### P2：增强资产治理

1. 账号、国家、币种、汇率、环境和时间全部参数化。
2. T1/T2/T3与功能Case使用引用关系，避免重复生成后再把duplicate计覆盖。
3. 生成后自动输出遗漏、冲突、重复、弱预期、无依据扩展和不可执行Case清单。
4. 支持需求变更后的影响分析和增量更新。

## 十、最终意见

这102条用例可以作为有结构的评审草稿，但不能直接证明需求覆盖，也不应直接作为发布门禁。平台当前最有价值的定位是“测试设计加速器＋风险提示助手”；在完成需求基线优先级、原子化追踪、冲突门禁、跨系统状态机和可计算oracle之前，不宜替代测试工程师的正式测试设计。
