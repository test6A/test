# 测试点生成平台专业评估报告

## 一、评估背景

评估对象：

- 人工基线：`PC马币下单项目-测试导图.mm`
- 平台产物：`mindmap-ai (1).mm`

评估目的：以人工测试工程师编写的测试导图作为基准，评价平台生成测试点的需求覆盖能力、正确性、可执行性、风险发散能力和落地价值，并给出平台改进建议。

术语说明：人工导图原始提取到 **475个叶子节点**，其中12个为空白节点、7个为备注/建议/待确认内容，清洗后得到 **456个有效人工需求检查点**；平台导图提取到 **178个平台叶子断言**。两者的叶子节点并不都等同于一条完整 Test Case，因此本报告评价的是测试设计内容，而不是简单比较用例条数。

## 二、管理结论

> **平台生成速度和测试发散能力合格，但需求收敛、正确性门禁、测试颗粒度、跨系统闭环和直接执行能力不足。当前产物适合作为测试设计初稿或灵感助手，不宜直接作为正式测试集，更不宜独立承担上线准入。**

平台最终评级：**C级——需整改**。

本次评估触发“不通过”硬门禁：

- 存在与人工基线相反的 P0 预期；
- 存在核心资金口径和历史快照遗漏；
- CES、订单员审批及 PO 关键链路未闭环；
- 平台测试点无法与需求检查点双向追踪。

最值得管理层关注的不是单纯的154项无候选检查点，而是人工确认存在 **16条错误平台测试点、涉及10个问题组**：遗漏意味着没有测试，错误测试则可能把正确实现判错，或者把错误实现判为通过。

| 质量维度 | 评价 | 结论 |
|---|---|---|
| 需求忠实度 | 存在免责声明、精度、只读、锁定时点等反向规则 | 不通过 |
| 完整性 | 强对应候选仅25.9%，154项无候选 | 不通过 |
| 可执行性 | 部分边界点明确，但大量使用“正确/一致”的复合预期 | 需整改 |
| 跨系统闭环 | PC较多，CES订单员和PO为0候选 | 不通过 |
| 风险发散 | 权限、越权、异常降级、事务副作用等补充有价值 | 有条件通过 |
| 可追溯性 | 无Requirement ID与Case/Assertion ID双向关系 | 不通过 |
| 可维护性 | 账号和实现细节硬编码，功能层与T1/T2/T3语义重复 | 需整改 |

## 三、覆盖率：采用“覆盖漏斗”

### 3.1 覆盖分层

| 自动覆盖层级 | 数量 | 占456项比例 | 解释 |
|---|---:|---:|---|
| 主题命中 | 302 | 66.2% | 能找到主题或业务词相近的平台内容，包含部分覆盖和错误覆盖 |
| 强对应候选 | 118 | 25.9% | 条件、操作和预期文本较明确；仍需排除口径冲突 |
| 部分对应候选 | 184 | 40.4% | 主题相同，但缺条件、字段级断言、公式、精度或锁定时点 |
| 无对应候选 | 154 | 33.8% | 未找到足够明确的平台对应内容 |

456个有效人工检查点的自动候选分类为：

| 最终分类 | 数量 | 占比 |
|---|---:|---:|
| 完整覆盖 | 118 | 25.9% |
| 部分覆盖 | 184 | 40.4% |
| 无覆盖 | 154 | 33.8% |
| **合计** | **456** | **100.0%** |

另经人工逐条复核，确认平台178个叶子断言中至少有 **16条错误测试点（9.0%）**，归并为10个问题组。错误测试点与人工需求点是多对多关系，不能用自动最佳匹配机械换算成一个“错误需求点数”，因此不把未经人工逐项签字的冲突传播数写入覆盖率分母。

### 3.2 建议对领导汇报的主指标

部分对应候选按0.5折算，无候选计0：

```text
加权覆盖候选率
=（完整 + 0.5 × 部分）÷ 有效人工检查点总数
=（118 + 0.5 × 184）÷ 456
= 46.1%
```

因此，本次建议采用“一个主口径、两个辅助口径”：

> **建议主报：强对应候选率25.9%（118/456）。**  
> **辅助：加权覆盖候选率46.1%；主题命中率66.2%。**  
> 46.1%仍是自动估算上限，因为118个强对应和184个部分对应中包含人工确认的错误平台测试点。早期的64.0%使用475个原始叶子且未清洗无效节点，只能视为粗粒度主题命中率。正式“有效通过率”必须在456项逐项人工签字后才能给出。

### 3.3 为什么178个平台点会“命中”302个有效人工点

- 人工导图颗粒度细，例如税、运费、返利、现金折扣、总计分别是独立检查点。
- 平台经常将其合并成“结算页各金额展示正确”一条综合断言。
- 178个平台点中，只有83条成为至少一个人工点的最佳匹配；其余95条可能是平台扩展、次优对应或内容偏离，需要继续分类，不能简单认定无效。
- 单个平台断言最高映射到40个人工检查点，说明存在明显的语义压缩和颗粒度过大问题。

规则建议：单个平台测试点映射超过5个人工检查点时，必须逐项列出独立断言，否则只能算部分覆盖。

### 3.4 计算和人工复核口径

1. 先解析两份FreeMind导图的完整路径和叶子内容，剔除12个空白叶子及7个明确的备注、建议或待确认项，形成456项有效分母；清洗项仍需需求负责人签字确认。
2. 匹配时完全打破模块限制，同时比较叶子正文、末三级路径和完整业务路径。
3. 统一MYR/马币/令吉、USD/美元、新增/新建、停用/禁用、只读/不可编辑等同义表达。
4. 使用业务概念锚点和内容相似度寻找最佳平台对应项：相似度≥0.50为强对应，0.38～0.49为部分对应，低于0.38为未覆盖。
5. 对默认值、肯定/否定、可编辑性、显示精度、越界处理、锁定时点等规则进行人工反向冲突复核；人工确认16条错误平台测试点。由于一个错误平台点可能关联多个需求点，不用自动最佳匹配推导“受影响需求点数”。
6. 两条端到端长链路由人工复核降为部分覆盖，因为平台只提到泛化审批和CES成功，没有逐角色、逐状态、逐字段断言。

剔除的7个非测试断言分别为：“正式系统建议替换为人员选择器”“以图为准”“显示这一块……显示的啥”“引流，套餐包”“保持不变，不在本次变更范围内”“这个页面返利需要……双币种的吗”“批次查询本次涉及吗”。

25.9%、46.1%和66.2%分别代表强对应候选、加权候选和主题命中，不能互相替代。正式对外验收建议由两名测试工程师对456项逐项盲审并签字；本报告已提供逐条证据，便于复算和提出异议。

## 五、平台产物做得好的地方

### 5.1 有一定风险发散能力

平台补充了人工导图未充分展开、但具有测试价值的场景：

- 接口级权限拦截，避免只隐藏按钮但接口可越权；
- 同一国家重复新增的唯一性校验；
- 汇率同步中的空值、0、负数、非数字过滤；
- 缓存和数据库不可用时的降级策略；
- 不同 `partnerCode` 用户确认订单的越权拦截；
- 订单状态及产品一致性校验；
- 失败时“不创建订单、不扣返利、不发审批、不抛CES”的事务完整性；
- 分享购物车后按接收方上下文重新计算；
- 金额筛选、排序按USD主金额的稳定口径；
- Chrome/Edge兼容测试。

### 5.2 主业务主题识别基本正确

平台能够识别币种配置、MYR/USD切换、汇率横幅、金额换算、订单锁定、Search Order、审批和CES等主要业务域，说明其需求主题抽取和常见场景扩展具备基础能力。

### 5.3 部分测试点具备较好可执行性

例如波动阈值0.1～50、缓冲天数1～30、金额精度0～4、无权限接口拦截等测试点，包含明确输入和结果，形式上优于只写“边界值验证”的泛化描述；但其中“越界后拦截”与人工基线“自动钳制到边界值”冲突，说明可执行性不能替代正确性审查。

## 六、平台核心欠缺点

### 6.1 需求事实与实现事实优先级错误

平台已经在测试点中标记“⚠️PRD-代码差异”，却仍然把代码行为直接写成期望结果。这说明平台能发现冲突，但没有正确处理冲突。

正确策略应为：

```text
需求/已确认业务结论 > 接口或设计文档 > 当前代码行为 > 模型推断
```

当PRD与代码冲突时，应输出“待确认问题”和两套候选口径，禁止擅自选择代码口径生成正式预期。

平台产物中可见11条“PRD-代码差异”、5条“Mock限制”和3条“目标规则”。这些标签说明平台已经识别信息来源不一致，但后续仍将其混入正式期望，缺少“发现冲突→停止定论→请求确认”的质量门禁。

### 6.2 颗粒度过大，主题覆盖不等于验证覆盖

典型平台断言：

> 商品、服务、税费、运费、返利、现金折扣和应付总额按MYR展示。

人工测试实际需要分别验证：

- 每个字段是否显示；
- 每个字段使用的USD原值；
- 换算公式和汇率来源；
- 币种符号；
- 舍入精度；
- 修改数量、服务年限、返利后的联动；
- 汇率锁定前后是否变化。

平台把多个断言合并后，执行人无法记录究竟哪个字段通过、哪个字段失败，也不利于自动化和缺陷定位。

### 6.3 缺少完整的需求追踪矩阵

平台没有稳定的 `Requirement ID → Case ID → Assertion ID` 映射，导致：

- 无法准确回答哪个需求被哪条测试覆盖；
- 无法区分完整覆盖和“顺带提到”；
- 无法在需求变更后做影响分析；
- 无法自动输出遗漏、冲突和冗余报告；
- 生成条数看似很多，但独立覆盖能力不可证明。

### 6.4 跨页面和跨系统状态链不闭环

平台对PC前台描述较多，但从“产品列表→购物车→结算→确认→成功→订单详情→审批→CES→PO”的状态传递没有形成统一的订单快照和字段校验链。

尤其是：

- CES订单员待审批：0%；
- CES订单员审批完成：0%；
- CES导出PO：0%；
- 极端场景：12.5%。

这意味着平台更擅长生成单页面功能点，不擅长生成跨角色、跨系统、跨状态的业务闭环。

### 6.5 正常流程偏多，变化时点组合不足

汇率和币种项目的核心风险不是单纯“能否显示”，而是何时更新、何时锁定、历史数据是否被污染。平台没有系统覆盖：

- 进入页面前更新汇率；
- 停留页面期间更新；
- 刷新、前进、后退；
- 进入确认页后更新；
- 提交瞬间更新；
- 销售下单后、渠道确认前更新；
- 审批中、CES确认前后更新；
- 配置停用后历史订单和再次下单。

### 6.6 测试数据和实现细节硬编码

平台测试点直接写入具体账号、`DW_GL_CORPORATE`、缓存/数据库实现等信息。若这些内容没有需求或环境依据，会造成：

- 测试点不可跨环境复用；
- 实现变化后大量用例失效；
- 把技术实现误当业务要求；
- 测试数据不可参数化维护。

## 七、明确错误点

| 优先级 | 平台测试点 | 人工基线 | 风险 |
|---|---|---|---|
| P0 | Admin不含中英文免责声明，前台不展示免责声明 | 人工基线明确要求中英文免责声明必填、编辑回显及前台展示 | 可能放过字段缺失和历史快照错误 |
| P0 | 编辑时国家可以重新选择 | 人工基线要求编辑时国家沿用并只读 | 可能把错误可编辑行为判为通过 |
| P0 | 金额精度默认4 | 人工基线默认2，范围0～4 | 默认配置验收错误 |
| P0 | 前台按配置精度展示 | 人工基线多处要求前台统一四舍五入2位 | 所有金额页面都可能被错误判定 |
| P0 | 确认页可以切换币种，仅不重取汇率 | 人工基线要求继承上一页币种并置灰不可编辑 | 破坏订单锁定语义 |
| P0 | 确认页仅参考展示，提交成功才真正锁定；与当前汇率不一致则拒绝 | 人工基线要求进入确认页即锁定，刷新保持；返回上一页再进入才更新 | 锁定时点和历史快照整体判错 |
| P1 | 波动阈值、缓冲天数、精度越界时提交拦截 | 人工基线要求输入越界后钳制到0.1/50、1/30、0/4 | 表单交互和接口预期错误 |
| P1 | 审计不要求字段级前后值 | 人工基线要求记录操作人、时间和修改前后值，并覆盖人工修正/通知人变更 | 审计验收缩水 |
| P1 | 记住用户上次选择的币种 | 人工基线未定义该持久化规则，Malaysia启用时强调默认MYR | 属于无依据业务规则，应转待确认 |
| P1 | UI只展示`DW_GL_CORPORATE` | 人工基线UI文案为“财务月度基准汇率”，其他暂未开放项可见不可选 | 可能混淆后台枚举和用户界面文案 |
| P1 | 自行增加导出免责声明 | 人工基线未把该文案定义为导出验收条件 | 需求外推断，不应当作正式通过条件 |

人工逐条确认至少16个平台叶子断言存在错误，归并为10个问题组。由于单个平台点可能关联多个细粒度人工检查点，而自动“最佳匹配”会把错误预期传播到不相关字段，本报告不虚构精确的“受影响需求点数”。正式签字评审前，应将这16条从所有覆盖候选中逐项排除。

## 八、重点遗漏点

### P0：影响金额正确性和订单闭环

- CES商务、订单员各状态下的币种、金额、审批状态和历史快照；
- PO中的Unit Price、Total Amount、Sub total、返利、现金折扣、Freight、TOTAL AMOUNT和币种；
- 产品列表、购物车、结算、确认、成功、订单/合同详情、审批各页面的字段级金额矩阵；
- 确认页后汇率、币种、免责声明锁定，后台修改不能污染历史订单；
- 7天内汇率变化后渠道确认仍使用销售下单历史汇率；
- 组合包下单品价格分摊和舍入尾差；
- 移动端及后台待办中受控、法务、销售审批的逐字段验证。

### P1：高频回归和配置管理

- Search Order的All、Pending、Closed页签一致性；
- MYR/USD订单在汇率变化、配置启停后的再次下单；
- 订单、合同、PO导出字段逐列校验；
- Admin弹窗标题、按钮、取消/X、必填标红、保存失败、防连点；
- 国家搜索、大小写、清空、单选、高亮、国家编码联动；
- 数字字段的输入、粘贴、非数字、步进按钮、边界和默认值；
- 修改时间格式及分页9/10/11条边界。

### P2：稳定性、兼容和体验

- 汇率极值、超长小数、逆向汇率精度和累计误差；
- 并发修改配置、提交瞬间汇率变化、重复提交和幂等；
- 多标签页、前进后退、会话过期和权限变化；
- 长免责声明、中英文切换、金额列溢出、分辨率和浏览器兼容；
- 缓存、数据库、CES、邮件中台的超时、重试、恢复和重复消息。

## 九、平台优化建议

### P0：先解决“生成错”和“无法证明覆盖”

1. **需求原子化**：先拆为唯一Requirement ID，每个原子点包含对象、条件、动作、规则和结果。
2. **来源优先级**：记录每个期望的出处；PRD与代码冲突时生成待确认问题，不生成确定预期。
3. **双向追踪**：输出 `Requirement ID ↔ Case ID ↔ Assertion ID`，支持一对多和多对一，但必须展示覆盖理由。
4. **冲突自检**：自动识别默认值、是否可编辑、是否展示、舍入精度、状态变化等肯定/否定冲突。
5. **原子断言门禁**：单条映射超过5个需求点时强制展开字段断言；“正确/正常/一致”没有量化预期不得计为完整覆盖。

### P1：提升业务闭环和测试设计能力

1. 建立“页面 × 金额字段”矩阵。
2. 建立“角色 × 审批状态”矩阵。
3. 建立“配置状态 × 订单生命周期”矩阵。
4. 建立“汇率变化时点 × 页面行为”矩阵。
5. 使用状态机生成PC、审批、CES、PO跨系统链路。
6. 对公式、精度、币种符号和历史快照生成可计算预期值，而不是“金额正确”。

### P2：增强平台工程能力

1. 参数化测试账号、国家、币种、汇率和环境变量。
2. 功能测试、T1/T2/T3使用同一Case ID引用，避免语义重复生成。
3. 生成后自动输出遗漏、冲突、弱预期、重复和需求外推断清单。
4. 支持需求变更后的影响分析和增量生成。
5. 输出UI、API、数据库、消息和下游系统的多层断言。

## 十、建议的平台验收指标

| 指标 | 建议门槛 |
|---|---:|
| P0需求完整覆盖率 | 100% |
| 总体严格有效覆盖率 | ≥90%，目标≥95% |
| 明确需求冲突 | 0 |
| P0遗漏 | 0 |
| 部分覆盖占比 | ≤10% |
| 需求与用例双向追踪率 | 100% |
| 无量化依据的“正确/正常/一致”预期 | ≤3% |
| 无需求依据的新增规则 | ≤1%，且必须标记待确认 |
| 人工无需修改接受率 | ≥85% |
| 测试设计评审工时降低 | ≥50% |
| 同输入重复生成的覆盖率波动 | ≤3个百分点 |

## 十一、建议整改后的复测方式

1. 固定本次456个有效人工检查点作为金标集，并保留475个原始叶子到456个有效点的清洗记录。
2. 给每个金标点增加Requirement ID、风险等级和明确期望。
3. 平台重新生成时不得读取人工测试答案，只读取需求材料。
4. 由两名测试工程师盲审“完整/部分/错误/遗漏”，分歧由第三人裁决。
5. 同时统计P0完整覆盖、总体有效覆盖、冲突率、弱预期率和评审工时。
6. 对同一输入重复生成至少3次，检查覆盖稳定性。

## 十二、最终意见

平台当前最大的价值是快速形成测试框架和补充常见异常场景；最大的风险是把“主题提到”包装成“已覆盖”，并在需求与代码冲突时选择了错误的事实来源。

建议短期定位为 **测试工程师的辅助工具**：平台生成后必须经过人工需求对齐和原子化拆分。只有当P0完整覆盖100%、明确冲突为0、CES/PO闭环完成、严格有效覆盖达到90%以上，才适合将其作为正式测试设计平台或上线准入依据。

逐条判定证据见：`平台测试点严格覆盖逐项证据-有效需求.md`。
